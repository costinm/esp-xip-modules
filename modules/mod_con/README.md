# mod_con

The text console of a device, in Rust: component 20 (`API.md`: `parse`, `render`, and the lines of the serial port), the commands `status`, `start`, `stop`, `reset`,
`heap`, `nv`, `wifi`, `help`, and `component.method key=value` calls: a request to a module by the catalog, or a native call through the table of a host component
(`wifi.set`, `power.sleep`, ...). Its manifest names the port `1` (the serial line, a link like any other), so every line typed is a frame of that link and what it says goes back to the source of the last line (`from`, `id`).

`src/tables.rs` is the catalog (the methods by name) and the native layouts (where the functions of the host components are) as Rust constants, generated by
`scripts/gen.sh` from the `API.md` files (`tools/catalog_rs.py`, until mesh-api-gen writes Rust for them). `crates/xip-runtime-host/tests/console.rs` runs it against
the host-runtime.

Things a Rust module must avoid, found while porting the former C console: a `match` or `const` array that returns `&str`/slices becomes a table of pointers
(`.data.rel.ro`, a relocation: the image is refused), and so does a value built from literals that rustc promotes to a static (`Parsed::Local("...")`).
Call per arm, or build the value at run time. The module build passes `-Zlocation-detail=none` for the same reason (panic locations hold file-name pointers).
